# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev       # start Vite dev server (http://localhost:5173)
npm run build     # production build to dist/
npm run preview   # preview the production build
npm run lint      # oxlint
```

There is no test suite in this project.

**Node version**: the system default `node` may be too old for this project's Vite version (which requires Node 18+). If `npm run dev`/`npm run build` fail outright, switch to a newer Node first, e.g. `nvm use 20`.

**Environment**: Supabase connection lives in `.env` (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`), read by `src/lib/supabaseClient.js`. `VITE_VAPID_PUBLIC_KEY` (see "Push notifications" below) lives there too — safe to expose, it's the public half of a VAPID key pair. `.env.example` documents the shape without values.

**Deployment**: see "Deployment: Cloudflare Workers" below — this is not a local-only project, it's live at a `*.workers.dev` URL, redeploying automatically on every push to `main`.

## Architecture

This is a single-page React app (Vite, plain CSS, `react-router-dom`) with **no backend of its own** — Supabase (Postgres + Auth + Realtime) is the entire backend, accessed directly from the browser via the anon key and secured entirely through Postgres Row Level Security. There is no Express/serverless layer; every read/write goes through `@supabase/supabase-js` and is authorized by RLS policies, not application code.

### Roles and route gating

Every user has a `profiles` row with `role` = `pending | athlete | coach | admin | removed` (set via a trigger on `auth.users` insert). `admin` is a read-only, in-team "athletic director" role — it sees everything a coach sees (roster, all logs, every conversation on the team, events) but can never write anything; every write-gated RLS policy and UI control checks for `coach` specifically, never `admin`. `AuthContext` (`src/context/AuthContext.jsx`) loads the session, checks `super_admins` (see below), then the matching `profiles` row, and exposes `user`/`profile`/`role`/`teamStatus`/`isSuperAdmin`. `App.jsx` is the single gate that decides what renders, in this order:

- no session → auth routes only (`/login`, `/signup`, `/create-team`, `/join`, `/install`), plus a pending-invite-aware `LoggedOutEntry` at `/` and the catch-all — see "Join + install flow" below
- `isSuperAdmin` → an entirely separate branch (see "Super admin" below) — checked **before** the role gates, since a super admin has no `profiles` row at all and so `role` is always `null` for them
- `role === 'pending'` or `null` → `PendingPage`, nothing else
- `role === 'removed'` → `RemovedPage`, nothing else
- `role === 'coach'` vs `'admin'` vs everything else (`athlete`) → **three separate `<Routes>` trees** defined inline in `App.jsx`, not a shared route set with permission checks. When adding a page, decide which tree(s) it belongs in and add the `<Route>` there (and to `NavBar.jsx` **and** `BottomNav.jsx` if it should be nav-linked — the two must stay in the same order/labels, see "Mobile & PWA" below) — there's no central route config to update elsewhere. The `admin` tree reuses the same page components as `coach` — each page hides its own write controls internally by checking `profile.role === 'coach'` (e.g. RosterPage's pending-signups section only fetches/renders for a coach).

A handful of pages (`EventsPage`/`EventDetailPage`, `MessagesPage`) are shared across all three trees and branch on `profile.role` internally instead of being duplicated. `WorkoutHistoryPage` used to be one of these (an athlete's own `/history`) but isn't anymore — the athlete tree has no History or Assignments routes at all now (see "Athlete calendar" below); `WorkoutHistoryPage` is only reachable via `AthleteDetailPage` (coach/admin viewing one athlete's history through the roster).

### Multi-tenancy: teams

Every team-scoped table (`workouts`, `running_segments`, `running_segment_reps`, `swim_segments`, `swim_segment_reps`, `bike_segments`, `bike_segment_reps`, `lifting_exercises`, `assigned_workouts` + its children, `conversations`, `conversation_participants`, `messages`, `workout_comments`, `events`, `event_entries`, `event_entry_athletes`, `team_settings`, `profiles`) has a NOT NULL `team_id`. It is **never trusted from the client** — a `BEFORE INSERT` trigger on each of those tables overwrites `team_id` with the value derived from the parent row (or, for tables with a direct owner column like `workouts.user_id`, from that user's own `profiles.team_id`), so no RLS `WITH CHECK` can be bypassed by lying about `team_id` even before it's evaluated. RLS policies then just compare `team_id = current_team_id()` (a `SECURITY DEFINER` helper reading the caller's own `profiles.team_id`), never inlining that subquery directly.

`teams.status` is `pending | active | rejected` and gates *write* access (not read) across the same set of tables via `current_team_status() = 'active'` (or `<> 'rejected'` for `team_settings`, which a founding coach is meant to keep editing while pending). A brand-new team's coach can view/adjust their own team's setup while pending, but can't approve roster changes, send messages, log workouts, or create events/assignments until a super admin approves the team. `TeamStatusBanner` (`src/components/TeamStatusBanner.jsx`) renders app-wide for `pending`/`rejected`.

Two ways to end up on a team:
- **Invite link** (`/signup?invite=CODE`) — `SignUpPage` resolves the code via the `get_team_by_invite_code()` RPC (the only thing granted to `anon`), then signs up with `team_id` in the auth metadata. `handle_new_user()` inserts the profile as `role = 'pending'`, same as always. `TeamSettingsPage`'s coach-facing invite link now points at `/join?invite=CODE` instead — the combined install+signup flow built on top of this same `/signup?invite=` path, see "Join + install flow" below.
- **Self-service team creation** (`/create-team`) — `CreateTeamPage` calls `create_pending_team()` (also `anon`-callable) to create a brand-new `status = 'pending'` team, then signs up against that team's id. `handle_new_user()` detects — purely from server state, never a client-supplied flag — that the target team has `status = 'pending'` **and** zero existing profiles, and makes that one signup `role = 'coach'` immediately instead of `'pending'`. Any other signup against that same team (even later while it's still pending) falls through to the normal `'pending'` path, since the team now has a member.

A signup with no `team_id` in its metadata (e.g. a Dashboard-created `auth.users` row) is left profile-less rather than failing — see "Super admin" below for why that matters.

### Super admin

Completely separate from the `profiles`/`teams` role system — a super admin has **no** `profiles` row and **no** `team_id`. Status comes exclusively from a row in the standalone `super_admins` table (`id` references `auth.users`, `email`, `created_at`). There is no INSERT policy on that table and no in-app path to grant it — the only way to create one is manual: a Dashboard-created `auth.users` row, followed by a one-time SQL insert into `super_admins`. Never route this account through the app's own signup.

Read access is intentionally the narrowest slice in the app, enforced at the RLS/RPC level (not just hidden in the UI — verified during this build via direct REST calls with a super admin's own bearer token, which return `[]`, not an error, for every team-scoped table):

- `get_team_stats()` — every team's name/status/created_at plus aggregate athlete/workout *counts only* (no `invite_code` — that's a credential, not a stat).
- `get_pending_teams()` — a pending team's founding coach name/email only, via a `SECURITY DEFINER` read of `auth.users` (the sole sanctioned path to that data; the client has no direct grant on the `auth` schema).
- `set_team_status()` — can only transition a currently-`pending` team to `active` or `rejected`, nothing else (no renaming, no touching an already-active team).

Every other table that previously had an `is_super_admin()` RLS bypass branch (`profiles`, `workouts`, `messages`, `conversations`, `team_settings`, `events`, etc.) has had that branch stripped entirely. `App.jsx` renders `SuperAdminHeader` (not `NavBar`) and a single route to `SuperAdminPage` for this branch — there are no team-scoped routes in it at all.

### Data layer convention

Every Supabase query is wrapped in a `src/lib/*.js` module, one per domain (`workouts.js`, `messages.js`, `assignments.js`, `events.js`, `teamSettings.js`, `workoutComments.js`, `teams.js`, `account.js`, `pushNotifications.js`, `splitRecorder.js`, `meetResults.js`). Pages and components call these functions and never import `supabaseClient` directly. Follow this pattern for new data access rather than inlining `supabase.from(...)` calls in components.

### Supabase schema — additive SQL files, run manually

There is no *migration* tooling wired up for schema changes — those are plain `.sql` files under `supabase/`, meant to be pasted into the Supabase SQL editor by hand, **in order** — see the full annotated list in "Project structure" above for what each one does; the run order is exactly the order listed there. The Supabase CLI (`npx supabase ...`, no local install needed) is used for one thing only: deploying the Edge Function (see "Push notifications" below) — `supabase functions deploy` and `supabase secrets set`, not schema/migrations.

Each file is written to be idempotent (`create table if not exists`, `drop policy if exists` before `create policy`, etc.) so it's safe to re-run. **Never edit a file that may have already been run against the live database** — add a new additive file instead, matching the existing naming/dating pattern, and note which prior file(s) it depends on in its header comment.

Non-obvious pitfalls hit repeatedly while building this schema, worth knowing before touching RLS or functions:

1. **`RETURNING` is filtered by the SELECT policy, not just the INSERT policy.** `supabase.from(x).insert(row).select()` asks Postgres to return the new row, which must pass that table's SELECT policy — not only the INSERT `WITH CHECK`. This breaks in a chicken-and-egg way whenever a SELECT policy depends on a related row that the same operation is *about to* create (e.g. a conversations table gated by "must already be a participant", inserted by the very user who isn't a participant yet). Fix: either drop `.select()` on that insert (generate the id client-side instead), or do the whole sequence inside a `SECURITY DEFINER` RPC, which bypasses RLS internally. See `get_or_create_direct_conversation` / `create_group_conversation` in the messaging schema files for the RPC pattern, and `createGroupConversation` in `src/lib/messages.js` for the client-generated-id pattern.
2. **Don't guess an auto-generated constraint name when altering it.** An inline `check (...)` with no explicit name gets a Postgres-assigned name that isn't guaranteed to match the `<table>_<column>_check` convention. `drop constraint if exists <guessed-name>` fails silently (no error, no effect) if the guess is wrong, so a later `add constraint` with the same guessed name creates a second, still-restrictive constraint alongside the untouched original. Look the real name up first via `pg_constraint`/`pg_get_constraintdef` and drop that — see the `conversations.type` or `workouts.type` constraint updates for the pattern.
3. **`CREATE OR REPLACE FUNCTION` can't change a function's return columns.** Changing a `RETURNS TABLE (...)` shape (e.g. dropping/adding a column) needs an explicit `DROP FUNCTION` first — `CREATE OR REPLACE` alone fails with `cannot change return type of existing function`. See the `drop function if exists public.get_team_stats();` in `standalone_super_admin_schema.sql`.
4. **A `RETURN QUERY` column type must match the declared return type exactly, not just "compatibly."** `auth.users.email` is `character varying`, not `text` — returning it uncast from a function declared `returns table (... founder_email text)` fails at *call time* (not at `CREATE FUNCTION` time) with `structure of query does not match function result type`. Cast explicitly (`u.email::text`) whenever pulling a `varchar` column into a `text`-typed return column.
5. **A trigger that only fires `AFTER UPDATE` misses rows created with the target state already set.** `add_user_to_team_conversation()` only ran on `AFTER UPDATE ... WHEN (old.role IS DISTINCT FROM new.role AND new.role IN (...))`, which by definition never fires for a row `INSERT`ed with that role already in place — exactly what happens for a founding coach (`INSERT ... role = 'coach'` directly, never a `'pending' → 'coach'` update). Fixed with a second, INSERT-scoped trigger sharing the same function (`founding_coach_team_channel_fix.sql`). Worth checking for the same gap any time a row can be created *already* in a state that's normally only reached via an update.
6. **`supabase_functions.http_request` (the trigger-based way to call an Edge Function from SQL) needs the `supabase_functions` schema, which isn't pre-provisioned on every project.** It's only created the first time a project sets up a Database Webhook — a committed SQL trigger calling it on a project that's never used Database Webhooks before fails with `schema "supabase_functions" does not exist`. The Dashboard's own webhook-creation UI provisions that schema automatically as a side effect, so that's the reliable path for a project's *first* webhook rather than trying to replicate it in raw SQL upfront — see `push_notifications_schema.sql`'s header comment, which only creates the underlying table there and leaves the webhook itself to the Dashboard.
7. **PostgREST's `.upsert(..., { onConflict: 'col1,col2' })` needs a real unique constraint on plain columns — it can't reliably target one defined on a jsonb expression index.** `push_subscriptions` originally tried a unique index on `(user_id, (subscription ->> 'endpoint'))` to dedupe by device without a redundant column; the client-side upsert couldn't resolve it. Fixed by duplicating `endpoint` as its own real `text` column with a plain unique constraint on `(user_id, endpoint)`, even though the same value already lives inside the `subscription` jsonb blob.

RLS leans on a small set of `SECURITY DEFINER` helper functions (`is_coach()`, `is_athlete()`, `is_admin()`, `is_super_admin()`, `is_conversation_participant(conv_id)`, `current_team_id()`, `current_team_status()`) so policies can check role/team/membership without recursing into RLS on `profiles`/`teams`/`conversation_participants` themselves. Reuse these rather than inlining the same subqueries.

### Workout data model

A "workout" is one row in `workouts` with `type` = `running | swim | bike | other | lifting | note`:

- `running` — optionally has child rows in `running_segments` (each segment has a `distance_value`/`distance_unit` and a generated `distance_meters` for cross-unit math) and `running_segment_reps` (per-rep times, supports interval/relay-style workouts with multiple reps per segment). Segments are optional — a running workout can be logged as just notes/effort with no segment breakdown.
- `swim` — same segment/rep shape as `running`, in `swim_segments`/`swim_segment_reps` (see `supabase/swimming_schema.sql`), just with `yards` added to the `distance_unit` option set (`yards | meters | miles`) since pool lengths are the common case. Entry UI is `SwimSegmentsEditor.jsx`, a thin per-type wrapper around the shared `SegmentEditor.jsx` (see "Workout log display format" below).
- `bike` — same segment/rep shape again, in `bike_segments`/`bike_segment_reps` (see `supabase/cycling_schema.sql`), with `distance_unit` restricted to `miles | km` (no track-length units). `bike_segment_reps` adds two OPTIONAL per-rep columns, `avg_watts`/`avg_cadence` — nullable, no default, shown alongside the time only when present (`summarizeBikeReps()` in `src/utils/format.js` averages them across only the reps that have a value). Entry UI is `BikeSegmentsEditor.jsx`, also a `SegmentEditor.jsx` wrapper.
- `other` — for aerobic cross-training that doesn't fit running/swim/bike (rowing, elliptical, hiking, stairmaster, etc). Same segment/rep shape again, in `other_segments`/`other_segment_reps` (see `supabase/other_segments_schema.sql`), but `distance_unit` is the widest set of any type (`miles | meters | km | feet | yards`) since cross-training activities span more units than any one sport does. Entry UI is `OtherSegmentsEditor.jsx`/`AssignedOtherSegmentsEditor.jsx`, mirroring Running's pair exactly apart from the unit list. This type originally logged just a duration (see `supabase/other_aerobic_schema.sql`) — widened to full segments in `other_segments_schema.sql` once it needed to feed the same weekly mileage math running/swim/bike do, see "Weekly mileage progress" below. Despite once being assumed to have "its own distinct structure" like lifting, `other` is structurally identical to `running` in every way, including its assigned per-rep targets (see below) — treat it as a fourth segment-based sport, not a lifting-like special case.
- `lifting` — child rows in `lifting_exercises`.
- `note` — a "quick log" with no children, just `date` + `notes`; both athletes and coaches can create these (everything else under `workouts` is athlete-only to write). `src/components/WorkoutListItem.jsx` is the dispatcher that renders the right card (`WorkoutCard` vs `QuickNoteCard`) based on `type` — render workout lists through it rather than choosing the card component yourself.

`assigned_workouts` (+ `assigned_running_segments` / `assigned_swim_segments` / `assigned_bike_segments` / `assigned_other_segments` / `assigned_lifting_targets`) mirror this same shape as coach-assigned targets. Each of the four segment-based types also has its own per-rep target table — `assigned_running_segment_reps` / `assigned_swim_segment_reps` / `assigned_bike_segment_reps` (added together in `supabase/assigned_segment_reps_schema.sql`) and `assigned_other_segment_reps` (`supabase/assigned_other_segment_reps_schema.sql`, added separately once `other` was recognized as not actually being lifting-like) — mirroring the actuals-side `running_segment_reps` etc. exactly, so a coach can prescribe a *different* target time per individual rep (e.g. 4x800m at 2:32/2:30/2:28/2:26) instead of one shared value applied to every rep. `assigned_bike_segments`/`assigned_bike_segment_reps` carry only a target time, never target watts/cadence, since those are actuals-only concepts an athlete logs. A segment's own legacy `target_time_hours/minutes/seconds` columns are left populated (from rep 1, as a fallback) purely for any code path that hasn't been updated to read the per-rep rows — nothing in this app relies on them once the reps exist; `assignmentToFormPayload()`/`LogWorkoutForm`'s assignment-prefill both read the per-rep rows first and only fall back to those columns for an assignment saved before this rework existed. `workouts.assignment_id` links a logged workout back to the assignment it fulfills; the same distance math also powers the athlete calendar's day-cell mileage (see "Athlete calendar" below) and the weekly progress meters (see "Weekly mileage progress" below).

`fetchRecentTeamFeed()` (the Team Logs home feed) excludes anyone with `role = 'removed'` via a query-level filter (`profiles!inner(...).neq('profiles.role', 'removed')`), not RLS — their logs are still fully intact and visible via Former Athletes → their detail page, just kept out of the active aggregate feed. See "Roster lifecycle" below.

### Workout log display format

Every place a log appears (Team Logs feed, an athlete's own history, a coach's athlete-detail view, the calendar's logged-day view) renders through the one shared `WorkoutCard` component (via `WorkoutListItem`) — there is no per-page reimplementation. The calendar's *not-yet-logged* assigned-day view (`AssignedWorkoutSummary.jsx`) is a separate component but reuses `WorkoutCard`'s own exported `SegmentLine` piece rather than duplicating the format.

**Collapsed thumbnail** — deliberately minimal, in order: `Total: {distance}{ @ time if complete}`, directly followed by `Prescribed: {distance}{ @ time if complete}` when the log fulfills an assignment, then `Effort: {n}/10` — the same `@ time` join used by every per-segment line below, not a different separator. Nothing else (no segment breakdown, no pace anywhere — pace was dropped from the log display entirely, see below). **Total time only shows when every segment's every rep actually has a time recorded** (`sumLoggedTimeSeconds`/`sumAssignedTimeSeconds` in `src/utils/format.js`, both all-or-nothing — a single missing rep across the whole workout means no total is shown at all, rather than a partial/understated one); the same all-or-nothing rule applies independently to the Prescribed line's own time. There is no field anywhere a coach/athlete can type a total time into directly — it's always this derived sum. A "View splits" toggle (same `<details>` pattern as "Coach comments") reveals the segment breakdown, shown whenever there's any segment data at all (actual or target).

**Expanded** = the same Total/Prescribed/Effort block as the thumbnail (not repeated a second time), plus, for each segment position (paired by index — a workout's logged segments are meant to correspond 1:1 to the assignment's target segments in entry order), the actual line directly above its prescribed line. Per-segment line shape: `{label}: {reps}×{distance}{unit} @ {times}` — the `@ times` part is dropped **entirely** when no time was recorded for any rep (never a placeholder like "—" or "0:00"), and an individual missing rep within an otherwise-filled list is simply left out of the comma-separated list (`formatRepTimesList()`) rather than shown as a gap-filler. The label is only stated on the actual line; the prescribed line directly below it drops the repeated label (unless there's no actual line at that position at all — e.g. `AssignedWorkoutSummary`'s not-yet-logged case — in which case the prescribed line keeps its own label, via `SegmentLine`'s `showLabel` prop, and its own top-level headline is labeled `Prescribed:` rather than `Total:`, since nothing's been logged yet). Bike's optional per-rep watts/cadence are appended after the times, actuals-only, same as before.

**No pace anywhere in the log display** (a deliberate removal, not an oversight) — running previously showed a per-segment/overall average pace; swim/bike/other never did. `formatTargetPace()` still exists and is still used, but only for the *entry* editors' live per-rep preview while typing (a genuinely different feature from viewing a saved log), not by `WorkoutCard`/`AssignedWorkoutSummary`.

**Entry form**: `LogWorkoutForm`'s "Total duration" for running/other is no longer a field the athlete/coach can type a value into directly (it used to allow a manual override, e.g. to account for rest/cooldown time the segments didn't capture) — it's now a read-only value calculated from segments (`allSegmentsComplete()`), shown only once every segment's every rep is filled in; otherwise it just displays "—". Swim/bike never had a manual total-duration field to begin with (no stored column; their total is always derived from segments at display time).

**The segment editors are one shared component now.** `SegmentEditor.jsx` is the single entry form used identically for athlete logging (actual times) and coach assigning (target times) — `RunningSegmentsEditor`/`SwimSegmentsEditor`/`BikeSegmentsEditor`/`OtherSegmentsEditor` and their `Assigned*` counterparts (8 files total) are thin wrappers configuring it (unit list, `labelPlaceholder`, `showPace` for the live preview, bike's `repExtraFields` for watts/cadence) rather than 8 independent copies of the same array-resize/move/remove logic. Both contexts use the same `repTimes: [{hours,minutes,seconds}, ...]` segment shape — `createAssignment()`'s `insertAssignedSegmentsWithReps()` is the assignment-side mirror of `insertRunningSegments()`/`insertSwimSegments()`/etc. in `src/lib/workouts.js`.

### Roster lifecycle: remove / reinstate / reject

Three different actions that look similar but do genuinely different things — worth not conflating:

- **Remove** (`RosterPage`, coach only, active athlete → `role = 'removed'`) — `remove_athlete()` RPC. Their workout logs are preserved (never deleted, never altered) but excluded from the active Team Logs feed as described above. Their own messages in the team channel and any group chats are **permanently deleted** (other members' messages in those same conversations are untouched); any DM they had with a coach is **deleted entirely** (the `conversations` row itself, cascading to its messages/participants) rather than just hidden. The confirmation dialog states both consequences explicitly.
- **Reinstate** (`FormerAthletesPage`, coach only, `'removed' → 'athlete'`) — a plain client-side `profiles` update, no RPC needed: `profiles_update_coach_only` already lets a coach set any role on any of their team's profiles, and the existing team-channel auto-join trigger fires on this exact transition and re-adds them for free. Their workout logs simply reappear in the feed (they were never removed from it in the database). Their deleted messages are **not** restored — that deletion was permanent by design.
- **Reject** (`RosterPage`'s pending-signups section, coach only, a `'pending'` signup that was never approved) — `reject_pending_profile()` **deletes the `auth.users` row outright** (`profiles.id` cascades automatically), not a soft-remove like the other two. This is deliberately different: a pending user can't have created anything worth archiving (RLS blocks all writes and the team-channel auto-join trigger never fires for `role = 'pending'`), and — the actual reason this matters — Supabase enforces email uniqueness at the `auth.users` level regardless of what `profiles.role` says, so soft-removing would permanently block that email from ever signing up again.

### Account self-service

`/account` (`AccountSettingsPage`, any logged-in athlete/coach/admin — not pending/removed/super admin) has three independent forms:

- **Name** — `update_own_name()` RPC. A narrow, `SECURITY DEFINER` function that only ever touches the `name` column, hardcoded to `auth.uid()` — deliberately not a general `id = auth.uid()` RLS policy, since RLS can't restrict which *columns* a client's `UPDATE` touches (a loose policy would let a client smuggle a `role`/`team_id` change through the same request).
- **Email** — `supabase.auth.updateUser({ email })` directly, no `profiles`/SQL involvement at all. Does not take effect immediately — Supabase's own "secure email change" flow requires confirmation via email first. This depends on the Supabase project having a working mailer (custom SMTP); the shared built-in dev mailer is rate-limited and not reliable for this.
- **Password** — `supabase.auth.updateUser({ password })`. Supabase's API has no "current password" concept (an active session is already proof of auth), so the product's explicit re-entry requirement is implemented by calling `supabase.auth.signInWithPassword()` with the claimed current password first — a wrong one fails clearly before anything changes.

### Messaging

`ConversationList` (`src/components/ConversationList.jsx`) is the single component behind both the desktop sidebar and the mobile single-pane list — there's no separate desktop-only component (`MessagesSidebar.jsx` was retired). Desktop renders it as a fixed 300px panel beside `ConversationView`; below the mobile breakpoint (640px) it becomes a full-width list, with `MessagesPage` toggling between the list and the open conversation via a `.messages-page-detail` class rather than separate routes. Its CSS classes still say `.mobile-inbox`/`.mobile-convo-*` — a naming leftover from when this really was mobile-only; it applies at every screen size now.

Each row shows a circular avatar (initials for DMs; a fixed two-person icon for groups, not initials — a numeral-prefixed group name like "800m" has nothing but a leading digit to build initials from, and since two different distance groups would otherwise collide on the same bare digit, an icon sidesteps the whole problem; the team channel gets a speakerphone icon on the team's own customizable accent color, never gray, so it always reads as the primary channel), a single-line preview (sender-prefixed for group/team, `"You: "` if the viewer sent it last), a relative timestamp, and an unread dot.

**Direct message pairing** (`get_or_create_direct_conversation()`, `supabase/coach_to_coach_dm_schema.sql`): a coach can DM any approved athlete on the team *or* any other coach (a solo-coach team's picker just shows an empty coaches list); an athlete can only DM a coach. Athlete<->athlete direct messages are rejected at both the RPC and the `participants_insert_direct` RLS policy (the RPC's own team-id/team-status checks predate this file — see `team_approval_schema.sql`). `ConversationList`'s "Start a conversation with…" picker (`openDmPicker`) mirrors this: a coach's candidate list merges `fetchApprovedAthletes()` and `fetchCoaches()` (minus themselves), with a small "Coach" badge to disambiguate the two in one merged list; an athlete's list is coaches only.

**Sort order** (`sortByRecency` in `MessagesPage.jsx`): team channel always first, then most-recent-activity first — not alphabetical, not grouped by type. A conversation with no messages yet falls back to its own `created_at`, so an empty group doesn't jump around relative to other empty ones as the list re-sorts.

**Last-message previews** (`fetchLastMessagesForConversations` in `src/lib/messages.js`): PostgREST has no "latest row per group" query, so this pulls the most recent 300 messages across the user's conversations (ordered newest-first) and keeps only the first (most recent) one seen per conversation. Fine at this app's scale; would need a real per-conversation query or a SQL view if a team ever had enough simultaneous conversation volume for 300 messages to stop covering everyone's latest.

**Unread tracking** (`src/utils/conversationReadState.js`) is client-side only — a localStorage "last seen" timestamp per conversation, not a schema column. A real read-receipt column would need a migration a coach would have to run by hand, same as every other schema change in this project; the localStorage version correctly shows/clears the dot but won't sync across a user's devices (read on the laptop, still unread on the phone). A conversation with no stored last-seen yet is treated as caught-up rather than unread, so shipping this feature didn't retroactively light up every existing conversation on first load.

**Mobile single-pane behavior**: `MessagesPage` auto-navigates a bare `/messages` to the team channel when one exists — a nice shortcut on desktop, where the list stays visible alongside the conversation regardless. On the mobile single-pane layout this would trap the user in the team channel permanently (tapping "Back" out of any conversation just re-triggers the same auto-redirect, since there's always a team channel to jump to) — worked around two ways: a `?view=list` query param the redirect explicitly checks for (so the Back link can request the list without being redirected straight back), and an `isMobileMessagesLayout()` (`matchMedia('(max-width: 640px)')`) check that skips the auto-redirect outright on mobile, so tapping "Messages" in the nav lands on the list there too instead of jumping into a conversation. Desktop's shortcut behavior is unchanged by either.

**Image messages** (`supabase/message_images_schema.sql`, `src/lib/messages.js`, `ConversationView.jsx`): a message may carry `content`, an `image_url`, or both — never neither (enforced by a DB check constraint; `content`'s original NOT NULL/non-empty constraint was dropped and replaced). Images live in a **private** Storage bucket (`message-images`, 10MB/`image/{jpeg,png,webp,gif}` limits enforced at the bucket level, not just client-side) — private, not public, is what makes the RLS-on-`storage.objects` actually matter, since a public bucket's URLs bypass RLS entirely. `image_url` stores the object's storage **path** (`{team_id}/{conversation_id}/{random-uuid}.{ext}`), never a URL — the path's own segments are what the storage RLS policies (`message_images_select`/`message_images_insert`) parse via `storage.foldername(name)` to re-derive the same team/conversation-membership checks `messages_select_participant`/`messages_insert_participant` already enforce on the table, just against path segments instead of columns. Because the bucket is private, a path is useless on its own — the client calls `resolveMessageImageUrls()` (batched `createSignedUrls()`, 1-hour expiry, same "resolve many at once" shape as `fetchLastMessagesForConversations`) to mint a signed URL at render time, re-resolved for any message (initial load, realtime insert, or the just-sent local one) whose path isn't already in the resolved map. Upload always happens **before** the `messages` insert, never after — an upload that succeeds but is never referenced by a message row is harmless orphaned Storage garbage (still fully RLS-scoped, invisible, safe to ignore), whereas inserting the message first would risk a visibly broken image with no retry path, since messages have no UPDATE policy. No `capture` attribute on the file input — that would force mobile straight to the camera and remove the "choose from library" option; `accept="image/*"` alone already gets both from the OS picker. `ConversationList`'s last-message preview falls back to "📷 Photo" for an image-only message, and the push notification Edge Function does the same for its body text.

### Push notifications

Opt-in only, off by default — `AccountSettingsPage` has two independent toggles ("Message notifications" / "Daily calendar notifications", backed by `push_subscriptions.notify_messages`/`notify_calendar` — see `supabase/notification_preferences_schema.sql`) that must be explicitly turned on; nothing is ever requested or sent without that. A device can have either, both, or neither on — turning one off never touches the other.

**Client side** (`src/lib/pushNotifications.js`): turning either toggle on calls `Notification.requestPermission()` from that click (never on page load — browsers require a user gesture, and a site only gets to burn that prompt once) via `ensureSubscribed()` if this browser has no subscription yet, then `setNotificationPreference(userId, 'messages' | 'calendar', true)` upserts `push_subscriptions` keyed on `(user_id, endpoint)` with that one column set true (preserving whatever the *other* column already was) — opting in from a second device adds a row rather than replacing the first, since each device's subscription has its own `endpoint`. Turning a toggle off just flips that column false, *unless* the other type is already off too, in which case the whole subscription is torn down (`disablePushNotifications()`) rather than leaving a row nothing will ever send to. `endpoint` is stored as its own plain column (duplicating a value already inside the `subscription` jsonb blob) because PostgREST's `upsert(onConflict:)` needs a real unique constraint on plain columns to target — it can't reliably resolve one defined on a jsonb expression index. A denied/blocked browser permission disables both toggles and shows an explanatory message instead of silently failing. iOS Safari has its own hard requirement on top of this, unrelated to anything in this codebase: Web Push only works for a PWA installed to the Home Screen, never a regular Safari tab, even though the `Notification`/`PushManager` APIs are technically present there too.

`push_subscriptions` (`supabase/push_notifications_schema.sql`) is deliberately **not** team-scoped like most tables in this project — it's purely user-owned, RLS restricts all client access to `auth.uid() = user_id`, and the only thing that ever reads across users is an Edge Function via the service role key (which bypasses RLS entirely). No `team_id`, no `BEFORE INSERT` trigger deriving one.

**Service worker** (`public/service-worker.js`) has `push` (shows the notification, using the app icon) and `notificationclick` (focuses an already-open tab on the target page, navigates one if none matches, or opens a new tab as a last resort) handlers — shared by both notification types below, since both just deliver a `{title, body, url}` payload the same way.

**Sending messages** (`supabase/functions/send-push-notification/index.ts`) is triggered by a Database Webhook on every new `messages` row: looks up the conversation's other participants, finds their subscriptions with `notify_messages = true`, and sends each one a Web Push notification (sender's name + a truncated message preview) via `npm:web-push`, using VAPID keys held as Edge Function secrets (`VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT`, set with `supabase secrets set` — never committed to this repo, unlike `VITE_VAPID_PUBLIC_KEY` which is safe to commit since it's meant to be public). Deployed with `--no-verify-jwt`, since the trigger is a database-level call with no end-user JWT to attach — see the function's own header comment for the trade-off reasoning (the endpoint ends up unauthenticated, judged acceptable here since the worst an outside caller could do is trigger push sends using data they supply, not read/write anything else).

**The webhook itself is set up by hand in the Dashboard, not in SQL.** `supabase_functions.http_request` (the mechanism a raw-SQL trigger would use to call an Edge Function) depends on the `supabase_functions` schema, which isn't pre-provisioned on every project — it's only created the first time a project sets up a Database Webhook, and the Dashboard's own webhook-creation flow provisions it automatically as a side effect. Confirmed the hard way: a committed SQL trigger attempting to call it failed with `schema "supabase_functions" does not exist` on this project, which had never used Database Webhooks before. `push_notifications_schema.sql` only creates the table + RLS for this reason; the webhook is: Dashboard → Database → Webhooks → table `messages`, event Insert, type "Supabase Edge Functions", function `send-push-notification`.

**Sending the daily calendar digest** (`supabase/functions/send-daily-calendar-digest/index.ts`) is a *scheduled* function, not webhook-triggered — there's no row-insert event to hook for "it's morning." It queries every athlete on an active team, combines their `assigned_workouts` for today with their team's `events` for today into one push per opted-in (`notify_calendar = true`) subscription, and skips anyone with neither today (no empty "nothing planned" ping). It has no way to know any user's timezone — nothing in this schema tracks one — so "today" is just the UTC date when the function happens to run; the cron schedule needs to be picked at a UTC hour that lands in the morning for wherever the team actually is. Deliberately doesn't share code with `src/utils/format.js`'s `summarizeAssignment()` — it reimplements a much simpler plain-text version, since a push notification body has no room for per-segment target times and there's no established path for sharing code between the browser bundle and a Deno Edge Function in this project.

**Scheduling it, set up by hand (same "not in this repo's SQL" reasoning as the messages webhook — see the function's own header comment):**
1. Deploy the function first: `supabase functions deploy send-daily-calendar-digest --no-verify-jwt`.
2. **Database → Extensions**: enable `pg_cron` and `pg_net` if not already on — without these, the Dashboard's Cron UI fails outright with `relation "cron.job" does not exist` (it queries a table `pg_cron` creates; confirmed the hard way setting this up).
3. **Integrations → Cron → Jobs → Create job**. Two job-type options: **"Supabase Edge Function"** (pick `send-daily-calendar-digest` from a dropdown — simplest, no URL/header typing) or **"HTTP Request"** (manual — endpoint URL is `https://<project-ref>.supabase.co/functions/v1/send-daily-calendar-digest`, `<project-ref>` being the actual ref from the dashboard's own URL, not literal angle brackets; needs an `Authorization` header — the key and value go in *separate* fields, value is `Bearer <service_role key>`, found under Project Settings → API).
4. Schedule expression is UTC (e.g. `0 11 * * *` for 11:00 UTC).
5. To verify it actually works without waiting for the schedule to fire: `curl -i -X POST https://<project-ref>.supabase.co/functions/v1/send-daily-calendar-digest -H "Authorization: Bearer <service_role key>"` — a healthy empty result looks like `{"athletesNotified":0,"sent":0,"failed":0}` (nobody had anything on today's calendar, or nobody's opted in yet — not an error). Function logs are under Edge Functions → send-daily-calendar-digest → Logs.

### Team color theming

`team_settings` holds one row **per team** (not a global singleton), RLS-scoped so each team only ever sees/edits its own row, editable by coaches (admin views, doesn't edit). `ThemeContext` (`src/context/ThemeContext.jsx`) fetches it on login and applies the palette as CSS custom properties directly on `document.documentElement` (`--accent`, `--accent-dark`, `--accent-bg`, `--accent-border`, `--accent-shadow`, `--accent-rgb`) — it does not use React state/props for coloring. All theme-aware CSS in `src/index.css` should reference these variables rather than hardcoding color values, so it stays responsive to a coach's palette choice.

**The default color is blue** (`#3b82f6`/`#1d4ed8`, the `PRESETS` list's "Blue (default)" entry in `TeamSettingsPage.jsx`) — rebranded from an original violet default (`#7c3aed`/`#5b21b6`, see `supabase/blue_default_theme_schema.sql`) to match the app icon/logo artwork once that was replaced with blue source art (see "Mobile & PWA" below). `ThemeContext` only ever applies whatever a team's own `team_settings` row already holds — it has no hardcoded fallback of its own — so this default lives in exactly two places outside the CSS/JS-side "if nothing has loaded yet" fallback: the `team_settings` table's own column defaults, and `handle_new_team()`'s explicit insert for every new team (both updated together, see that schema file's header comment). The **CSS `:root` values** (`src/index.css`) are a separate, third thing — the actual rendered color for any page with no team at all (logged-out auth pages, the super-admin branch) or the brief window before a logged-in user's own theme finishes loading, never touched by `ThemeContext` itself; `public/manifest.json`'s `theme_color` and `index.html`'s `theme-color` meta tag (OS/browser chrome tinting) follow the same default and need updating alongside it by hand, same as the CSS.

**Sport-type colors are deliberately NOT part of this theme.** `--running`/`--swim`/`--bike`/`--other`/`--lifting`/`--note` (used for `WorkoutCard`/`QuickNoteCard`'s left-border accent, `WorkoutTypeIcon`, and the `type-badge` classes) are fixed values in `:root` that `ThemeContext` never touches — the whole point is that the same sport always reads the same color regardless of which team's page you're on, which only works if a coach's custom accent color can't override them. The dashboard `MetricCardRow` tiles use a third, separate fixed trio (`--metric-week`/`--metric-athletes`/`--metric-event`) for the same reason, chosen to be visually distinct from the sport palette so a metric card is never mistaken for a sport indicator. When adding any new fixed-color UI, follow this pattern (a plain `:root` value, never `var(--accent...)`) rather than accidentally wiring it into the team theme.

### Events & calendar

The "Calendar" tab (renamed from "Events" — nav label and page `<h1>` changed; the route is still `/events`, plus `/` for athletes, see "Athlete calendar" below) defaults to the month calendar (`view` state, `'calendar' | 'list'`, toggled via a `.type-toggle` pair with Calendar first/left) — the flat list is the supplement now, not the default. Both views read from the same `events` array fetched once by the page.

`EventCalendar`'s month grid (`buildMonthGrid()`) always renders a full 7-column grid for alignment, but leading/trailing days from adjacent months render as blank, non-interactive `<div>` placeholders (`calendar-cell-outside`) rather than showing that neighboring month's dates or events — only the selected month's own days are ever clickable or show a dot/event-name indicator. Month/year jump is via two `<select>` dropdowns (in addition to Prev/Next/Today); the year dropdown's option range is recomputed off whatever year is currently in view (not a fixed range off today), so it always contains a valid selection even after navigating far away.

**Today's cell** gets a light `--accent-bg` tint across the whole cell plus a bolded date number (`.calendar-cell-today`), additive on top of the pre-existing small filled-circle date number rather than replacing it — the circle alone read as too subtle to call "today" out at a glance once the rest of the redesign toned down borders elsewhere.

**Events have a real `category`** (`meet | team_event | other`, `supabase/event_categories_schema.sql`, defaults to `'other'`) — before this, `events` had no type/category field at all, unlike `assigned_workouts`/`workouts` which already had sport types. `EventForm` gets a `Category` `<select>` (labels centralized in `EVENT_CATEGORY_LABELS`/`eventCategoryLabel()` in `src/utils/format.js`, next to the existing `WORKOUT_TYPE_LABELS` convention), and `EventCard` shows a `type-badge cat-{category}` chip alongside its existing content. Each day cell shows one dot per event, colored by category (`.calendar-cell-event-dot.cat-{meet|team_event|other}`, new fixed `--event-meet`/`--event-team`/`--event-other` colors in `:root`) — following the *exact* same established pattern as the pre-existing per-assignment workout dots (`.calendar-cell-assignment-dot.type-{sport}`, fixed `--running`/`--swim`/etc colors), not a new convention. The `cat-*` class namespace (vs. `type-*` for sport) exists specifically so event's own `other` category never collides with workout's `other` sport type despite sharing a name.

`CalendarLegend.jsx` — the app's first legend/color-key component — renders above the grid (both the coach's team calendar and an athlete's own, since it's the one shared `EventCalendar`) explaining both dot families as two small grouped clusters ("Workouts": Running/Swimming/Cycling/Lifting/Other; "Events": Meet/Team event/Other) rather than one merged flat list, again specifically because both families happen to have their own "Other" entry with a different meaning.

Editing an event happens **in place**: `EventsPage` owns all the form/editing state and bundles it into one `editing` object (`{ editingId, form, setForm, onSubmit, onCancel, saving, error }`) passed down through `EventCalendar` to `EventCard` — whichever `EventCard` instance matches `editing.editingId` renders the shared `EventForm` component in place of its normal display, instead of a separate form opening elsewhere on the page. This works identically whether the card is in the plain list or inside the calendar's day-detail panel, since both render through the same `EventCard`. Creating a new event is unrelated to this — it still opens `EventForm` in a fixed spot at the top of the page (`formOpen` state), since only editing was asked to happen inline.

### Coach assignment grid, Logs tab, and quick-create

`CoachAssignmentsPage` is also the coach/admin home page (`/`, as well as `/assignments` — both routes render the same component, the same dual-route pattern the athlete tree already used for `/` + `/events`). It defaults to Grid for coaches (`view` state, `'grid' | 'splits' | 'list'` — the third tab is still internally called `'list'` even though its button now reads "Logs"; Grid first/left; admin never sees the Grid button at all — `canCreate` gates it — so admin's effective view is always Logs regardless of the default).

**The Logs tab's content changed twice from its original design, worth knowing the history of if touching it again:**
1. Originally a flat, ungrouped `.assignment-row` list (with the multi-athlete-select + single date + `AssignmentForm` above it, unchanged since before Grid existed) — just a plain list of every assignment ever created below that, no date scoping at all.
2. Reworked into day-grouped cards (`AssignmentDayGroup.jsx`, since deleted — see step 3) with a rolling week window + Prev/Next nav, mirroring `AssignmentGrid`'s own week-nav pattern, to fix both the "spreadsheet card" look and the fact the flat list had no date bound at all.
3. **Team Logs — a previously-separate standalone page/nav destination (`TeamFeedPage.jsx`, since deleted) — was folded into this same Logs tab**, stacked below the day cards at first, then promoted above them once the day-grouped assignment list itself was judged redundant with Grid (which already shows the same assigned-workouts data in table form) and dropped entirely. **The Logs tab today is *only* the old Team Logs content**: metric cards (`MetricCardRow`, this-week logged count / active-athlete count / days-to-next-event), a date-or-athlete filter (`filterMode` state, `'date' | 'athlete'`), `WeeklyMileageSection` when a specific athlete is selected, and the filtered `workout-list` of actually-logged workouts (`WorkoutListItem`) — i.e. purely a "what's actually been logged" browsing view, never assignment planning. `fetchRecentTeamFeed()`/`fetchTeamWorkoutsByDate()`/`fetchWorkouts()` (all in `src/lib/workouts.js`) power this exactly as they powered the old `TeamFeedPage`.

**Creating something now goes through a single "+" entry point, not always-visible inline forms.** The page-header "+ New" button (desktop, `.page-header-inline-action`) and the mobile `Fab` (same `onClick`) both open a `Modal` with a small chooser: **"New Workout"** (the athlete-checklist + `AssignmentForm` that used to sit permanently inline at the top of the Logs tab, now only rendered inside this modal) or **"Quick Note"** (`QuickNoteForm`, whose own header toggle button — "+ Quick note" — is gone the same way). This exists because a coach can only ever do one of two things here — assign a workout, or post a quick note (never log a full workout on an athlete's behalf, see "Workout data model" above) — and the chooser makes that explicit rather than showing two separate always-on forms. The button is visible on every tab (Grid/Logs/Record Splits), not just Logs, since it's no longer tied to revealing an inline section on one specific tab. Submitting either form just closes the modal and shows a toast; there's no on-page list left to refresh in response (Grid/Splits manage their own fetches independently, and the Logs tab's own `loadLogs()`/`refreshFeed()` re-run after a note post specifically, not after an assignment).

`AssignmentGrid.jsx` — athletes × Mon-Sun, one week at a time, sticky header row + sticky first column inside an `overflow: auto` wrapper (this app's first two-axis-sticky table). Fetches a rolling 14-day window (`[weekStart-7d, weekStart+6d]`) via `fetchAssignmentsForCoach({startDate, endDate})` on every week-nav — the extra week behind is what lets "Copy previous week" work without navigating there first.

**Cell styling**: a filled cell renders as a rounded, sport-tinted card (`.grid-cell-card`, background/border via `color-mix()` against the same fixed `--running`/`--swim`/`--bike`/`--lifting`/`--other` sport colors used everywhere else — see "Team color theming" above) with the sport's `WorkoutTypeIcon` + label on top and the existing `summarizeAssignment()` segment text below, plus a small `--success`-green checkmark badge (`.grid-cell-check`) in the corner when `status === 'completed'` — the badge is deliberately the same color regardless of sport (the card itself already conveys sport type) so a coach can scan the whole week for green checkmarks without learning a per-sport meaning for the badge too. An empty cell is a dashed rounded "+" placeholder rather than plain text. The athlete column gets a small neutral initials avatar (`getInitials()`, the same single-letter convention `ConversationList`'s own DM avatars use) next to the name — kept in an inner `<span class="grid-athlete-row">` flex wrapper rather than `display: flex` directly on the sticky `<th>` itself, so the table's existing sticky-column behavior is never touched.

**Editing/deleting an assignment**: the child segment/target tables (`assigned_running_segments` etc., including the per-rep `assigned_running_segment_reps` etc. — see "Workout data model" above) only have SELECT + INSERT RLS policies, never UPDATE/DELETE — so "edit" is `deleteAssignment(id)` (the coach-only DELETE policy on `assigned_workouts` already existed; children `ON DELETE CASCADE`) followed by a normal `createAssignment()`, never an in-place update. `assignmentToFormPayload()` (`src/lib/assignments.js`) converts a fetched assignment's nested snake_case rows back into the camelCase shape `AssignmentForm`/`createAssignment` expect, for both pre-filling an edit and building a copy/paste clipboard entry — reading each rep's own target time back from its per-rep child rows, not just the legacy segment-level column.

**Known trade-off, not a bug**: editing or paste-overwriting an assignment the athlete has already logged against unlinks that log (`workouts.assignment_id` is `ON DELETE SET NULL`, and there's no coach-write path to `workouts` to relink it afterward — adding one would be a new RPC). The athlete's log itself is preserved; only the target-vs-actual link and completed status are lost. Both the cell modal and the paste-overwrite confirmation show an explicit, stronger warning for this specific case rather than doing it silently.

**Export day** (`CoachAssignmentsPage`'s date picker + "Export as PDF" button, coach-only): fetches that single day's assignments, then opens `ExportDayModal.jsx` as a review step before anything downloads — athletes are auto-grouped by identical workout (`groupAssignmentsByWorkout()`, the same grouping Split Recorder's defaulting reuses), and the coach can move an individual athlete into a different group or reorder the groups themselves (e.g. "Group B" above "Group A") before exporting. Purely client-side staging — none of this writes back to `assigned_workouts`, it only changes how `downloadAssignmentsPdf()` (`src/utils/assignmentsPdf.js`) lays the PDF out. This toolbar is hidden specifically on the Record Splits view (see "Split Recorder" below) since there's nothing to export from that view.

**Copy/paste**: click-drag (`mousedown`+`mouseenter`+document-level `mouseup`), ctrl/cmd-click (additive, non-contiguous), or shift-click (rectangle from the last anchor) builds a `Set<"athleteId|dateStr">` selection. A touch-only "Select mode" toggle makes taps additive instead of opening the cell modal, since there's no drag-select equivalent on touch. The clipboard is `{ athleteOffset, dayOffset, payload }[]`, relative to the selection's anchor at copy time — a selected cell with no assignment contributes nothing. Paste has two modes depending on clipboard size: **1 cell → broadcast** the same payload to every cell in the new target selection (covers "same day, different athletes" and "same athlete, different days" as one rule); **>1 cells → anchor mode**, ignoring the target selection's shape entirely and laying the clipboard's relative offsets out from just its anchor point (covers row-copy and full grid-to-grid paste; offsets landing outside the loaded roster or the visible week are silently dropped, never wrapped/clamped). "Copy previous week" is a one-click preset through this exact same path — a synthetic clipboard of the whole previous week anchored at the current week's first athlete row + Monday — not separate logic. Paste execution runs through a small local `mapWithConcurrency` (concurrency 5) rather than one unbounded `Promise.all` or slow sequential awaits, since a full grid-to-grid paste can be up to 50 athletes × 7 days; after the batch settles it just refetches the 14-day window rather than hand-patching local state.

### Split Recorder

A third view on `CoachAssignmentsPage` alongside Grid/List (`view === 'splits'`, coach-only — same `canCreate` gate as Grid), for a coach entering live workout splits for the whole roster at once during a practice, saving straight into each athlete's log rather than through the normal one-athlete-at-a-time `LogWorkoutForm`.

**Why this needed a new RPC, not a plain insert**: every `workouts` write RLS policy but `workouts_insert_own_coach_note` requires `user_id = auth.uid()` — a coach has no path to insert/update a running/swim/bike/other row (or its child `{type}_segments`/`{type}_segment_reps` rows) for anyone but themselves, and quick notes are self-authored, not on-behalf-of-an-athlete. Rather than loosening RLS across all four sports' segment/rep tables, `supabase/split_recorder_schema.sql` adds one coach-only `SECURITY DEFINER` RPC, `record_split_recorder_entry()` — the same "privileged write into someone else's row" pattern already used by `remove_athlete()`/`reject_pending_profile()`. It handles running/swim/bike/other only (never lifting — a "split" is a rep time, which lifting has no equivalent of) via dynamic `{type}_segments`/`{type}_segment_reps` table names, since all four share the exact same shape. The existing `set_workout_team_id`/`validate_workout_assignment`/`complete_assigned_workout` triggers already fire correctly on the inserts/updates it performs, so `team_id`, assignment-athlete matching, and the assignment's completed-status flip all just work without this function duplicating any of that logic.

**No manual setup at all beyond a day picker — this is a deliberate simplification, not the original design.** Two earlier revisions of this tool had progressively more setup UI: first one shared name/type/distance/columns field applied to every athlete, then (once that proved wrong — see below) a coach-editable list of "fallback" segments alongside a type toggle and name field. Once every athlete's columns were already being derived entirely from their own assignment data (see the next paragraph), that whole panel had nothing left to do except for the rare athlete with no assignment at all — clutter for the common case, kept only for an edge case. It's gone now. `resolveAthlete()` in `SplitRecorder.jsx` computes type, segments, `assignmentId`, and an auto-generated name (segment labels/generated names joined with `, `, the same style `computeSetupDefaults()` used to build for the old shared-name field) purely from that athlete's own assignment for the day; an athlete with no running/swim/bike/other assignment (no assignment at all, or a lifting one) simply has nothing to record against — their whole row renders as `N/A`, and the page shows a note pointing the coach at Grid/List to create an assignment first, rather than offering a second, redundant way to define one inline.

**Each athlete's columns come from their OWN assignment, not one shared structure.** The very first version of this tool built one shared column set and matched each athlete's own assignment segments back onto it — first by array position, then, after that produced a real bug, by content (distance/unit). Both were fundamentally the wrong shape for this problem: different athletes can be assigned genuinely different workouts the same day (that's the whole point of showing every athlete regardless of their assignment — see the grid's own row below), so there is no single column set that's simultaneously correct for an athlete doing 2mi + 4x400m + 4x200m and another doing 3mi + 4x200m + 6x100m. `flattenSegments()` turns one athlete's own resolved segments into that athlete's own column list (one column per rep, in segment order), computed per athlete (`perAthleteResolved`/`perAthleteColumnDefs`), never against a shared list. A column's own prescribed time (`prescribedSecondsForDef()`) is trivially correct — no matching or guessing involved, since the column was built directly from that exact assigned segment in the first place.

**The grid is `display: grid`, deliberately not an HTML `<table>`.** Two earlier revisions reused `AssignmentGrid`'s table-based sticky-first-column approach (`.assignment-grid-wrap`/`.assignment-grid`), patched one mobile Safari table+sticky quirk after another — first the sticky name column didn't stick at all (`border-collapse: collapse`, the base `.assignment-grid` rule, is a known WebKit trap for `position: sticky` on table cells; switching to `separate` fixed it on `AssignmentGrid` itself but not here), then two adjacent-but-independent sticky cells per athlete (a header-row name cell and a blank data-row cell below it) stuck inconsistently with each other (merging them into one `rowSpan={2}` `<th>` fixed *that*), and then — still on mobile Safari only — the rowSpan combined with sticky broke column alignment itself (header labels and data cells rendered shifted by one column). Three rounds of table-specific WebKit quirks was the signal to stop patching and rebuild on CSS Grid instead, whose sticky + row-span support is far more consistent across browsers than HTML tables'. `grid-template-columns` is set inline per render (`minmax(150px, auto) repeat(maxColumns, minmax(90px, 1fr))`, since the column count is dynamic); `.split-recorder-grid` needs `width: max-content` for the same reason the old table needed it — a plain block element's `width: auto` fills its container rather than sizing to its own (wider) content, which would silently defeat the ancestor `.assignment-grid-wrap`'s `overflow: auto` horizontal scrolling.

There is no single shared header row — since different athletes' columns can mean different things, **every athlete gets three consecutive grid rows: a sticky name cell (`.split-recorder-name-cell`, `position: sticky; left: 0`, spanning the next two rows via an inline `gridRow: 'span 2'` — the span count itself is fixed at 2, not dynamic, since every athlete always has exactly a header row + a data row) directly followed by their own header-row-of-labels (`.split-recorder-header-cell`) and data-row-of-inputs (`.split-recorder-value-cell`)**, labeled `{distance}{unit} ({rep#})` (e.g. `400m (1)`, `400m (2)`, rep numbering restarting at 1 within each segment, not cumulative across them), with a subtle left-border divider (`.split-recorder-segment-start`) where one segment's reps end and the next begin. Every athlete's row is padded out to `maxColumns` — the longest of anyone's own column count, or every column for an athlete with no assignment at all — with the extra columns rendered as a plain, non-editable `N/A` cell (`.split-recorder-na-cell`), never an empty fillable input and never another segment's data. Each real cell's `TimeTextInput` `placeholder` is that column's own prescribed time when its assignment has one, else the ordinary `e.g. 6:45` hint.

**Display order is reorderable per session, separately from the roster's own alphabetical order.** `athleteOrder` (`SplitRecorder.jsx`) is local component state — an array of athlete ids, reset to alphabetical every time a new day loads — that the coach can freely rearrange with the ▲/▼ buttons on each athlete's header row (`moveAthlete()`, e.g. to match the order athletes will actually run in). It's reconciled against the live `athletes` prop at render time (`orderedAthletes`) rather than kept in sync via a separate effect — any id no longer on the roster is dropped, any athlete not yet in the stored order (newly approved mid-session) is appended at the end. This never touches `fetchApprovedAthletes()`'s own alphabetical ordering, which every other consumer (`AssignmentGrid`, etc.) still gets unchanged.

**Column layout changes reset the grid's entered times, deliberately.** `entries` (the coach's in-progress typed times) is keyed by flat column index *per athlete*, so anything that resizes any athlete's own column count would otherwise leave stale values misaligned once things shift — in practice now, that only happens when a fresh day's assignments load, since there's no more coach-editable structure to resize mid-session. `loadDay()` always replaces `entries` wholesale (never patches it) for exactly this reason. `TimeTextInput` only ever reads its `value` prop once, on mount (see that component's own header comment), so replacing the state alone isn't sufficient on its own: the grid wrapper's `key` includes a `columnLayoutKey` (every athlete's own column count, alongside `date`) to force a full remount whenever a load actually changes the layout, the same trick already used for switching days.

**Saving** (`recordSplitEntry()` in `src/lib/splitRecorder.js`, fanned out via the same bounded-concurrency `mapWithConcurrency()` `AssignmentGrid`'s paste uses, now shared from `src/utils/concurrency.js`): only athletes with at least one filled-in cell *anywhere* are sent at all. Per athlete, each of *their own* segments is rebuilt independently from just its own columns — only the reps that athlete actually has a time for (`buildAthletePayload()`, a cell left at `0:00` — `TimeTextInput`'s own "nothing typed" value — is dropped, same "zero means unfilled" convention `formatRepTimesList()` already uses elsewhere, not a broken fixed-width segment with gaps), and a segment nobody filled in for that particular athlete is left out of their payload entirely rather than sent as an empty one. Every athlete saved this way always has a matching assignment (that's the only way they get any columns at all now), so their log always links to it (`assignment_id`) and the existing target-vs-actual comparison and completed-status flip work exactly as they do for a normal log.

**Partial saves / resuming later**: `workouts.source` is a nullable marker column (`'split_recorder'` or null, added by this same schema file) that exists purely so `record_split_recorder_entry()` can find and update its *own* previously-recorded entry in place — matched on `(athlete, date, type, source = 'split_recorder')` plus assignment linkage — rather than guessing from name/date alone, which could otherwise collide with and silently overwrite an athlete's own unrelated manually-logged workout that happens to share a name. Reopening the recorder for a day re-fetches and re-populates the grid from whatever was already saved (`findExistingEntry()`/`buildInitialEntries()` in `SplitRecorder.jsx`) — each athlete's own current columns are matched against their own previously-saved segments by content (`matchSegmentsToSaved()`, by `(distance_value, distance_unit)` first, label only as a tiebreaker among same-distance candidates, never positional), so a coach can save mid-practice and keep adding times before a final save without ever creating duplicate logs, and a saved entry still lines up correctly even if the athlete's assignment changed distances between saves. A saved segment only ever holds however many reps were actually filled in last time (gaps are dropped at save time, not preserved), so reopening places them in the first N columns of the matching segment — there's no way to recover which original column a compacted rep came from, and for a live-recording tool that distinction isn't meaningful anyway. The RPC still defends against one case the client can't rule out on its own: if an athlete's assignment is already fulfilled by a *non*-recorder log (they logged it themselves before the coach got to it), it never contests that link — it saves the recorder's entry as a standalone unlinked one instead of overwriting or double-linking, even though every *other* recorder-created entry is always linked now that the client only ever builds columns for an assigned athlete in the first place.

The Export-day PDF toolbar (date + "Export as PDF") is hidden on the Record Splits view specifically (`view !== 'splits'` in `CoachAssignmentsPage.jsx`) — it's Grid/List-only functionality with nothing to export from this view, and stayed visible here it was pure clutter on an already-busy live-entry screen.

**Display**: a saved entry is a completely ordinary logged workout — same `workouts`/`{type}_segments`/`{type}_segment_reps` rows a normal `LogWorkoutForm` submission would create — so it renders through the exact same `WorkoutCard` everywhere any other log does (Team Logs, athlete history, the calendar), with no separate display path of its own.

### Meet Results (Record Results mode)

A "Record Results" toggle on `EventDetailPage` (`RecordResultsPanel.jsx`, coach-only, alongside the existing "Lineup" view — see `supabase/meet_results_schema.sql`) lets a coach record race-day results directly against a meet's lineup (`event_entries`/`event_entry_athletes`, see "Meet lineup" above). A sibling to the Split Recorder, not a variant of it — no shared tables, RPC, or components — since a Split Recorder session is a coach entering live splits for a whole roster at once during a single practice, while meet results come in one finished event entry at a time, in whatever order events at the actual meet happen to finish. Each lineup entry has its own "Save results" button and can be saved independently, any time, with only some athletes filled in — the same "save now, come back later" partial-completion pattern the Split Recorder established, just at per-entry granularity instead of a whole-grid one.

**Two kinds of result:**
- An **individual result** — a solo event, or one athlete's own relay leg split — creates/updates a real logged `workouts` row for that athlete (`type: 'running'`) via the coach-only `record_meet_result()` SECURITY DEFINER RPC (`src/lib/meetResults.js`), the same "coach writes into someone else's row" pattern `record_split_recorder_entry()` already established (RLS otherwise only lets an athlete write their own workouts). A group of athletes all running the same race shares one splits grid (`ResultSegmentsGrid`, defined inside `RecordResultsPanel.jsx`) — one column per split, one row per athlete — rather than a full segment editor per athlete, so a coach fills a whole heat at once instead of one athlete at a time; a coach with only a finish time just sees one column. A relay leg split stays a single `TimeTextInput`, since one leg is already atomic. The workout's `name` is the lineup entry's own event name (e.g. "800m"), and `notes` states `Meet result — {event name}` so it reads clearly as a race result, not a practice log, anywhere logs appear (Team Logs, athlete history, the calendar) — it renders through the exact same `WorkoutCard` as any other log, no separate display path.
- A **team-level relay result** (the whole squad's one finish time), entered as a plain `TimeTextInput`, is stored on a new `event_entry_results` table, keyed by `(entry_id, team_label)` — it deliberately does **not** create any per-athlete workout, since attributing an unsplit relay time to one individual's personal log wouldn't be accurate. It's visible only on the Record Results view itself. A relay squad can have a team result, individual leg splits, or both at once — they're independent and don't overwrite each other.

**The splits grid** (`ResultSegmentsGrid` in `RecordResultsPanel.jsx`) is a CSS Grid, deliberately not an HTML `<table>` — the same reasoning as Split Recorder's own grid (see that section above): a dynamic column count is unreliable on mobile with a table. Unlike Split Recorder, which needs a separate header per athlete since different athletes can have completely different practice assignments the same day, a Record Results group is always the *same race* for every athlete in it, so one shared header row covers everyone — genuinely simpler than Split Recorder's per-athlete three-row layout, not just a smaller version of it. Each athlete's own segments (`initialSegments()`, same function backing the grid as backed the earlier one-editor-per-athlete design) are flattened into columns (`flattenColumns()` — a segment with `reps: 3` becomes 3 columns, one rep each), and the grid's column count is the widest of any athlete in the group; an athlete with fewer or differently-shaped columns (e.g. an old result saved before `split_count` existed) gets non-editable "N/A" cells for the columns they don't have, the same convention Split Recorder's own grid uses. Typing into a cell doesn't touch the grid's column *shape* — only `segmentDrafts`' underlying segments/rep-times — so the grid is purely a fast way to fill in *times* across a group; changing which splits exist at all still goes through `split_count`/re-recording, not the grid itself.

**Two independent panes, not a sticky first column.** The athlete-name column (`.result-grid-names`) and the scrollable splits (`.result-grid-scroll`) are two separate flex siblings sharing a `--result-row-h`/`--result-names-w` CSS custom property pair so their rows line up, rather than one grid with `position: sticky` on its first column. This was a real, on-device bug, not a preemptive choice: sticky combined with a dynamically-set inline `grid-template-columns` inside an `overflow-x: auto` wrapper reliably collapsed the whole grid to a single column on iOS Safari specifically — identical markup and data rendered correctly on desktop, broke only on an iPhone PWA. Splitting into two panes means the name column never needs sticky behavior to "stay visible" — it's simply never part of the horizontally-scrolling element at all. Mobile sizing (`@media (max-width: 640px)`, right in this same CSS block) also bumps `--result-row-h`/`--result-names-w`/font sizes well past their desktop values — the original complaint wasn't just the grid's overall width but that individual cells/tap-targets were too small to use comfortably on a phone.

`.result-grid-scroll`'s own width is `calc(100% - var(--result-names-w))`, not `flex: 1` — another on-device (unconfirmed root cause, but reproducible) iOS quirk: `flex: 1` sizing an `overflow-x: auto` sibling next to a fixed-width pane, when that sibling's own child is an extremely wide (`width: max-content`, e.g. 13 columns × 150px) CSS Grid with a dynamically-set column count, was observed rendering at a small fraction of its correct width — confirmed via directly fetching and diffing the deployed CSS/JS bundle against source to rule out a caching/deploy explanation first. An explicit `calc()` tied to the same `--result-names-w` custom property `.result-grid-names` itself uses removes any dependency on flex-grow resolving this specific layout correctly.

**Column width is computed in JS, not a CSS custom property** — `useIsNarrowViewport()` (`RecordResultsPanel.jsx`) tracks `window.innerWidth <= 640` (matching the same breakpoint every other mobile rule in this grid uses) and interpolates a real pixel number directly into the inline `grid-template-columns` (`repeat(maxColumns, minmax(${colWidth}px, 1fr))`), unlike row height and names-pane width, which stay as `var(--result-row-h)`/`var(--result-names-w)` referenced from plain CSS. This is deliberately inconsistent with the rest of the grid's sizing approach, on suspicion of a WebKit bug resolving `var()` specifically inside `repeat()`/`minmax()` — narrowing columns still rendered far too small on-device even after the sticky and flex-width bugs above were both fixed, and this was the next-most-likely explanation once deployment/caching had already been ruled out by diffing the live bundle against source.

**The actual bottleneck turned out to be one level up, in `.lineup-row` itself, not anywhere inside the grid.** `.lineup-time` (`min-width: 5rem`, never shrinks) and `.lineup-actions` (never shrinks — on Record Results specifically, it holds the whole "Save results" button, 130px+) don't wrap, and since `.lineup-details` has `min-width: 0` (so it *can* shrink arbitrarily small), `.lineup-row`'s own `flex-wrap: wrap` (`@media (max-width: 640px)`) never actually triggers — the browser just squeezes `.lineup-details`, and everything inside it including the entire splits grid, into whatever sliver is left on the same line as the time and the button, no matter how the grid's own internal CSS is tuned. `.result-entry-row .lineup-details { flex-basis: 100% }` (same media query) forces it onto its own full-width line below them instead — scoped to `.result-entry-row` specifically since the plain Lineup view's own `.lineup-actions` (compact ↑/↓/Edit/Delete link-buttons) is narrow enough to never trigger this in the first place. Every other Record Results mobile-sizing fix in this section was real and independently verified (via diffing the deployed bundle against source), but had no visible effect on-device until this one, since they were all tuning the size of content inside a container that was itself being starved of width one level higher up.

Segments default to a single column seeded from `parseEventDistance()` (`src/lib/meetResults.js`) parsing the lineup entry's free-text event name — "800m" → 800 meters, "2 Mile" → 2 miles, "5K" → 5 km, "4x400m Relay" → 400 meters (the individual leg distance, which is what a leg-split result actually wants), and even a bare number with no unit at all ("1500", "800", "4x400 Relay") — very common in practice, since everyone already knows a bare track-event number means meters; takes the *largest* number in the name (not the first) so a relay's squad-size prefix or a heat label like "Heat 2 - 400" doesn't get mistaken for the distance itself — unless the entry itself already requests auto-splits (see below). `event_entries` has no structured distance field at all, only `event_name`, so there's nothing else to seed a `running_segments` row from. A name with no recognizable distance (a field event like "Long Jump", or a relay's own team name) falls back to a nominal 1 meter for that seed segment — a harmless quirk of the display machinery (a real distance is required by the schema) for what's expected to be a rare, mostly-out-of-scope case, not a lie about the result: the workout's own `name` still states the real event. `record_meet_result()` takes the same `p_segments` jsonb shape `record_split_recorder_entry()` does (see `split_recorder_schema.sql`) rather than a flat distance/time — one RPC covers both "just a finish time" and "full interval splits," no separate simple/detailed path — and caches the segments' total time on `event_entry_athletes.result_hours/minutes/seconds` so the panel doesn't have to join out to `running_segments`/`running_segment_reps` just to show "does this athlete have a result yet."

**Auto-splitting a race into even intervals** (`event_entries.split_count`, an optional "Splits" field on `EventEntryForm` — e.g. "4" for a 1500m) seeds every athlete in that entry with the same interval template via `computeEvenSplitSegments()` (`src/lib/meetResults.js`), instead of each coach hand-building "400, 400, 400, 300" per runner. It's not a literal even division (1500m ÷ 4 = 375m flat, which nobody actually splits a race at) — it rounds the target interval to the nearest 100m first (the way a coach actually thinks about it: "about 4 splits" on a 1500m means 400m reps with whatever's left over), takes as many full reps of that rounded size as fit, and — matching this app's existing "4x400m" convention rather than four separate one-rep segments — collapses them into one segment with a `reps` count, plus a final shorter segment for the remainder (dropped entirely if it's under ~50m, e.g. the ~9m left splitting a 1609.344m mile into 400s — not a real interval anyone would time). Always computed in meters regardless of the race's own parsed unit, since splits are called out in meters even for a mile-labeled race. This is purely a per-entry *default* recomputed fresh by `initialSegments()` every time a coach opens an athlete with no result yet — nothing about it is persisted as actual segment rows until the coach hits "Save results," and an athlete who already has a saved result always shows their own real segments instead, regardless of the entry's `split_count` (see "Partial saves" below) — so changing `split_count` after some results are already in never retroactively rewrites anyone's recorded splits.

**Relay detection is a coach-overridable guess, not inferred from group size alone.** Nothing in the schema actually marks a lineup entry as a relay — a `team_label` group with more than one athlete is just as often several teammates each entered individually in the same open event (e.g. three athletes all in "800m") as it is an actual relay squad, so `RecordResultsPanel` can't trust "more than one athlete" to mean "relay." `looksLikeRelay()` (`src/utils/lineup.js`) guesses from the event name instead (`/relay/i` or an "NxN" pattern like "4x400"), and every multi-athlete group gets its own "Relay squad" checkbox seeded with that guess but always overridable — getting this wrong in either direction would be a real correctness bug (individual entrants wrongly excluded from their own logs, or a genuine relay's athletes wrongly given individual race credit for a leg they didn't run alone).

**Partial saves / resuming later**: `event_entry_athletes.result_hours/minutes/seconds` + a `workout_id` FK (added by `meet_results_schema.sql`) are the source of truth for "has this athlete's result been recorded, and what is it" — unlike the Split Recorder, which has to reconstruct that identity fuzzily from date/type/source, this table already owns the (entry, athlete) pair outright, so an explicit FK is simpler and exact. Re-opening Record Results rebuilds each athlete's segment editor from their linked workout's own `running_segments`/`running_segment_reps` (embedded via that FK in `fetchEventEntries`'s select — see `src/lib/events.js`), not just the cached total. `RecordResultsPanel` only resends a field/segment set on "Save results" if the coach actually touched it this session (tracked in local `drafts`/`segmentDrafts` state) — an untouched athlete's already-correct saved data is left alone rather than redundantly resent. Since `TimeTextInput` only ever reads its own `value` prop once, on mount, the panel forces every input (including each cell inside `ResultSegmentsGrid`) to remount after a reload — a `resultsVersion` counter bumped on every entries refetch, folded into each input's `key` — so a freshly-saved value is actually visible, not just correct in the database. The same "remount via a changing key" trick the Split Recorder already uses for its own day/column-layout changes.

### Athlete calendar: logging, assignments, and mileage

Calendar is the athlete's home (`/`) — `EventsPage`'s athlete branch additionally fetches `fetchAssignmentsForAthlete()` and *all* of `fetchWorkouts({userId})` (unfiltered by date), then passes `assignments`/`workoutByAssignment`/`workoutsByDate`/`canLog={true}` to `EventCalendar`. Coach/admin pass none of this, and `EventCalendar` behaves exactly as it did before any of this existed.

**No standalone Log Workout / History / Assignments tabs for athletes** — all three were folded into Calendar. `LogWorkoutPage` still exists at `/log` and `/edit/:workoutId` (not nav-linked, kept only as a direct-URL fallback) but is now a thin wrapper around `LogWorkoutForm`, which takes `workoutId`/`initialAssignmentId`/`initialDate` as plain props instead of reading route params/query string. `EventCalendar` opens `LogWorkoutForm` directly in a `Modal` from the day panel — no navigation at all, so logging/editing never leaves the calendar; `onSaved` closes the modal and calls `onWorkoutSaved` (= `EventsPage`'s `load()`) to refetch. `AthleteAssignmentsPage` was deleted outright (nothing else referenced it), not just unlinked, since the calendar day panel now fully covers what it did.

**Day panel, for an athlete**: every day is clickable, not just ones with events/assignments (`disabled={!canLog && !hasEvents && !hasAssignment}`), since logging isn't gated on having anything assigned. The log/edit button lives *inside* whichever card is showing that day's info (the assignment card, or a plain workout card when there's a log but no assignment) rather than floating below the list — only a genuinely empty day (nothing to attach it to) gets a bare standalone button. Button label/target: an existing log for the day → "Edit workout"; else an assignment exists → "Log this workout" (prefills type/segments/targets *and* the date — a pre-existing gap where an assignment's date was never actually applied to the log is fixed as part of this); else → "Log a workout" (blank, just the tapped date).

**Mileage on day cells** (`dayMiles()` in `EventCalendar.jsx`): running/swim/bike/other are all converted down to one miles figure for now, rather than each sport's own natural unit, via `sumLoggedDistanceMiles()`/`sumAssignedDistanceMiles()` (`src/utils/format.js`) — running's (and, since it was widened to segments, other's) logged total already lives in `workouts.total_distance` (miles, populated by `LogWorkoutForm`); swim/bike have no such column, so their segments are summed the same way assigned-target segments are. Actual logged mileage always wins over the assigned target the moment a distance-type log exists for the day, whether or not it fulfills an assignment — a day logged with no assignment at all still shows its mileage. Styled muted-gray for "assigned, not yet logged" vs. bold and sport-colored (`--running`/`--swim`/`--bike`/`--other`) for "actually logged", echoing the existing pending-vs-complete dot convention.

**Coach editing an athlete's assignments from the calendar** (`CalendarAssignmentModal.jsx`): when a coach has a specific athlete selected via `EventsPage`'s athlete-picker dropdown (see "Events & calendar" above), `EventCalendar` gets `canManageAssignments={true}` plus `coachId`/`targetAthleteId`/`targetAthleteName`/`otherAthletes`, and the day panel grows a parallel "Edit assignment" (existing assignment) or "New assignment" (none yet) button alongside — never combined with — the athlete's own log/edit action, since `canLog` stays `false` for a coach viewing someone else's calendar. Unlike `AssignmentGrid`'s cell modal (which this deliberately doesn't share code with — same reasoning as the app's other per-context-not-shared editors), creating a brand-new assignment this way also offers an "Also assign to…" checklist of the rest of the roster: checking any of them broadcasts the same payload to their calendar for that date too, **replacing** their existing assignment for that date if they have one (delete-then-recreate, same as everywhere else assignments are "edited" — see the coach assignment grid section above for why). Editing an already-existing assignment has no broadcast option, same single-cell scope as the grid's own edit.

### Weekly mileage progress

`WeeklyMileageSection` (`src/components/WeeklyMileageSection.jsx`) renders four per-sport progress meters — running, swim, bike, other, all by distance in miles — for a given athlete's current Mon–Sun week, with Prev/Next navigation (`Next` disabled once the viewed week is the current one; there's no way to browse into the future). It's the same component in every place it appears:

- The athlete's own dashboard — `EventsPage`'s athlete branch (`/`, see "Athlete calendar" above), always visible regardless of the Calendar/Events toggle.
- A coach's read-only view of one athlete — `AthleteDetailPage` (always), `EventsPage`'s Calendar tab when a coach/admin has a specific athlete selected from "View athlete's calendar" (only in the calendar view, since that's where the picker lives), and `CoachAssignmentsPage`'s Logs tab (see "Coach assignment grid, Logs tab, and quick-create" above) when its own "Select by athlete" filter has one chosen — hidden again the moment any of these falls back to its default all-athletes/team view.

**The goal is derived, not coach-set.** For a viewed week, `weeklyAssignedTotalsBySport()`/`weeklyLoggedTotalsBySport()` (`src/utils/weeklyMileage.js`) sum that week's `sumAssignedDistanceMiles()`/`sumLoggedDistanceMiles()` (`src/utils/format.js`, the same functions the athlete calendar's day-cell mileage already uses) across every fetched assignment/workout — so the "goal" a meter fills toward is just whatever the coach assigned that athlete that week, however it was assigned (grid, flat list, or the calendar's per-athlete assignment modal), and it updates the instant an assignment changes. **This wasn't the original design** — `supabase/weekly_goals_schema.sql` first shipped a real coach-set-and-saved weekly goal (its own table, effective-dated so a past week was judged against whatever goal was in effect then) with a form on `AthleteDetailPage`. That table and form were removed outright (`supabase/remove_weekly_goals_schema.sql`) in favor of the assignment-derived approach above, once it was clear the two coach-facing concepts (assigning workouts, setting a goal) were redundant — the two schema files are kept, in order, as history rather than edited away, per this project's additive-only schema convention.

**The four shapes** (`SportProgressMeter.jsx`) are bespoke inline SVGs, not a charting library: an oval running track and a winding bike road (closed/open paths respectively, `pathLength="100"` + `stroke-dasharray`/`stroke-dashoffset` revealing proportionally, exactly like a circular progress ring), a swim pool with a bottom-anchored rect rising as a water level, and an "other" heartbeat/pulse line revealing left-to-right (same stroke technique as the road). Fill is capped at 100% even when the actual total exceeds goal — the text below still shows the true total (e.g. "27.3 / 25 mi"). The fill `<path>`/`<rect>` is only rendered when `pct > 0`: at exactly 0%, `stroke-dasharray:100`/`stroke-dashoffset:100` sits precisely on the dash/gap boundary, which rendered as a stray visible dot (the round line-cap) even with nothing logged — omitting the element entirely at zero was the fix, rather than trying to tune the dash math. No goal for a sport (or a 0/0 week) shows a plain "`current` mi" with an unfilled shape instead of hiding that meter — all four stay present for a stable layout.

### Mobile & PWA

**Nav** (`NavBar.jsx` + `BottomNav.jsx` + `Fab.jsx`): above ~860px, `NavBar`'s full row of links shows (icons + labels, same order for coach/admin: Workouts/Calendar/Messages/Athletes/Team Theme, Account appended after). Below that width, `NavBar`'s own links/user info hide entirely and `BottomNav` takes over — a fixed bottom tab bar with the same first four items (icon + label `NavLink`s) plus a "More" button opening a `Modal` listing whatever didn't fit (Team Theme, Account, Log out for coach/admin; just Account, Log out for athlete). Both `NavBar` and `BottomNav` are always mounted (in `App.jsx`, alongside each other); which one is *visible* is CSS-only (`display: none`/`flex` on the same 860px breakpoint) — the same "always render both, let CSS decide" technique the old hamburger toggle used, just split across two components instead of one drawer now. `Fab` is the mobile-only floating "+" button replacing a page's inline top-of-page create button (see e.g. "Coach assignment grid, Logs tab, and quick-create" above) — same breakpoint, same technique, via each page's own `.page-header-inline-action` class hiding below 860px while `.fab` hides above it. `SuperAdminHeader` has no drawer *or* `BottomNav` at all — a super admin has no nav links, just identity + logout, and is explicitly out of scope for this whole redesign — so it carries a `.navbar-simple` class the mobile CSS explicitly excludes from the "hide `.navbar-user` below the breakpoint" rule; without that exclusion its logout button disappears on mobile with nothing to replace it (this was a real, shipped bug for a while — worth checking for the same gap any time a `.navbar`-using header doesn't have a `BottomNav` fallback).

**PWA install**: `manifest.json` + `service-worker.js` + `index.html`'s `apple-mobile-web-app-*` meta tags (iOS Safari ignores `manifest.json` for install/standalone behavior and needs its own tags) make the app installable. Icons (`favicon.svg`/`favicon-16x16.png`/`favicon-32x32.png`/`apple-touch-icon.png`/`icon-192.png`/`icon-512.png`) are all plain resizes of `public/app-front.png` — a square, opaque, rounded-icon composition (black background, no alpha) — with no cropping needed since the source is already square. `logo.png` (the nav bar logo) is the one exception, and needs more than a resize: `app-front.png` is actually two separate glowing elements — the infinity/heartbeat mark *and* a rounded-square border frame around it — plus a soft ambient haze filling the rest of the canvas (a deliberate atmospheric vignette, not pure black; it never fully reaches zero brightness even far from either element, which is why a plain brightness-threshold cutout leaves a visible torn/jagged edge). `logo.png` keeps only the mark, isolated as its own connected component: `scipy.ndimage.label` on a `brightness > 190` mask (the *max* of R/G/B per pixel) picks out the mark and the border frame as the two largest components, distinguishable by bounding-box span — the frame's spans nearly the full canvas, the mark's doesn't. Alpha is a Gaussian falloff by distance from that component (`exp(-(dist/12)^2)`) so the mark's own glow fades smoothly rather than being hard-clipped, **gated** by the pixel's own brightness (`clip((brightness-70)/(255-70), 0, 1)`, zeroing out alpha wherever the source pixel is itself dark) rather than multiplied by it — the glossy-tube rendering in this artwork has a genuinely dark shading line running down the middle of each stroke, and gating (not just weighting) is what keeps that line from surviving as an unwanted dark outline in the final cutout. Color is used directly from the source with no un-premultiply step. If `app-front.png` is ever replaced, redo this whole extraction for `logo.png` and re-tune every one of these numbers by eye (they are specific to this artwork's own brightness/glow characteristics, not universal constants — the values above already changed once, from an earlier purple source image, when the art was replaced with this blue one) — the other icons still just need a plain resize.

**Service worker caching**: page navigations and everything else in `public/` (favicon, logo, manifest, icons) are network-first with a cache fallback for offline use — those keep a stable filename even when their contents change, so cache-first would serve a stale copy forever after any rebrand. This was also a real shipped bug once: the original fetch handler cached "everything same-origin," on the assumption it was all Vite's hashed build output, and a browser that had cached the old logo kept serving it regardless of later deploys. Only `/assets/*` (Vite's actual build output, content-hashed per file) is cache-first now — that's what makes repeat visits load instantly without ever risking staleness. `offline.html` is precached and served as a last-resort fallback for a failed navigation with nothing else cached yet.

### PWA reliability: resume from background, stuck loading, service worker updates

Fixes an infinite-loading bug: reopening the installed PWA after it had been backgrounded/suspended for a while could get stuck loading forever, recoverable only by force-closing and reopening the tab.

**The root cause and its fix**: `AuthContext`'s session/profile check gates the *entire* app's render (`App.jsx` shows nothing else while `loading` is true), and had no timeout — a phone suspending the tab's network stack long enough for the in-flight request to silently die left `loading` stuck `true` forever. `SESSION_TIMEOUT_MS` (10s) now guarantees it always resolves either way; a timeout sets `authError` instead, which `App.jsx` surfaces as a "Tap to retry" screen (`retry` re-runs the same check) rather than either an infinite spinner or bouncing an already-logged-in user to `/login` just because of a transient hiccup. `AuthContext` also re-runs this same check on resume (see below), since a connection that silently died while backgrounded won't otherwise recover until something re-triggers it.

**`src/utils/appResume.js`**: `onAppResume(callback)` fires when the app returns to the foreground after being backgrounded — `visibilitychange` (the primary signal) plus a bfcache `pageshow` restore (`event.persisted`, notably iOS Safari, which can restore a backgrounded PWA from the back-forward cache rather than re-running any top-level module code at all), debounced together so both firing in close succession only triggers one recovery pass. Wired into: `AuthContext` (re-verify the session), `ConversationView` (re-fetch messages *and* tear down + recreate the realtime channel — a Supabase Realtime websocket can silently die during a long suspend with no close/error event, so a stale "subscribed" channel can't be trusted), `MessagesPage`/`CoachAssignmentsPage`/`EventsPage` (re-fetch their own data), and `UpdateBanner` (re-check for a new service worker version).

**`src/utils/withTimeout.js`**: races a promise against a hard timeout (`~9s` at most call sites) so a fetch that never settles rejects instead of hanging a loading state forever. Applied to the same set of call sites as `onAppResume` above, each showing a "Retry" button next to the resulting error rather than an indefinite spinner.

**Service worker updates** (`UpdateBanner.jsx`, mounted in `main.jsx` outside the auth-gated tree so it works even on the login page): owns the service worker registration itself, moved here from a plain top-level script in `main.jsx` — a real gotcha hit doing this: a `window.addEventListener('load', ...)` attached from inside a React effect can attach *after* `load` already fired (effects run after mount, unlike a synchronous top-level script), which would silently never register the service worker at all; fixed by checking `document.readyState === 'complete'` first and registering immediately in that case. `public/service-worker.js` already called `self.skipWaiting()`/`clients.claim()` (a new version takes over an already-open tab immediately, not waiting for every tab to close) — `UpdateBanner` detects exactly that moment via the `controllerchange` event and shows a "Refresh" prompt, but only when this page was *already* controlled by a service worker at load time (`hadController`, captured once at mount) — a fresh install's first `clients.claim()` also fires `controllerchange`, and that's not an update worth prompting about. Also calls `registration.update()` on resume (via `onAppResume`), since a browser only checks for a new service worker script on navigation by default and this app can stay open/backgrounded for a long time without one.

### Join + install flow

`/join?invite=CODE` is the combined "install the PWA + sign up for a specific team" page — the one link `TeamSettingsPage` now generates for coaches to share, replacing a bare `/signup?invite=` link (which still works directly; `/join` is built on top of the same `resolveInviteCode()` path `SignUpPage` uses). `/install` is the same install UI with no team attached, for a plain (no-invite) install link. Both share `InstallInstructions.jsx` — platform-detected: a real one-tap button via `beforeinstallprompt` wherever the browser supports it (Android Chrome, desktop Chrome/Edge), step-by-step manual instructions for iOS Safari (which has no install API at all), a generic fallback otherwise, and "you're already using the installed app" when `display-mode: standalone`/`navigator.standalone` is already true.

**The problem this solves**: an installed PWA's `start_url` is always `/` (see `manifest.json`) — someone who visits `/join`, installs to their home screen, and only opens the app later (or after fully closing everything first) would otherwise lose the `?invite=` query string the moment they relaunch from the icon, landing on a bare `/` with no idea which team they were joining.

**`src/utils/pendingInvite.js`**: the moment `/join?invite=CODE` is visited, the code is saved to `localStorage` (key `pending_invite_code`, `{code, savedAt}`, 7-day expiry) — regardless of whether the code even resolves to a real team yet, so a genuinely valid code still survives an install even if that particular check fails from a transient network blip. `App.jsx`'s logged-out `/` route and catch-all (`LoggedOutEntry`) recover a still-valid saved code on next launch and redirect straight to `/signup?invite=CODE` with it applied. Explicit routes like `/login` are deliberately **not** covered by this redirect — an existing user consciously navigating there shouldn't be hijacked into signup just because some earlier invite code is still sitting in this browser's storage. `SignUpPage` clears the saved code (`clearPendingInvite()`) immediately after a successful signup, so it can't bleed into a later, unrelated signup on the same device. An expired or corrupted entry is dropped and cleared the next time it's read, not left to linger.

### Design tokens

`src/index.css` defines a spacing scale (`--space-1`…`--space-10`, 4px-based), radius/shadow/transition tokens, and a small type scale in `:root`, plus light/dark overrides via `prefers-color-scheme` (no manual theme toggle). Card-like surfaces across the app share one grouped selector for consistent radius/shadow/hover treatment rather than each component defining its own. Shared UI primitives — `Skeleton`/`SkeletonList` (loading placeholders), `StatRow` (dashboard stat tiles), and the toast system (`ToastContext` + `useToast()`, mounted once in `main.jsx`) — should be reused for new pages rather than re-implemented.

**Depth over borders**: most card-like surfaces (roster rows, event/workout cards, forms, panels — the same shared selector above) use `box-shadow: var(--shadow-sm)` for definition against the page background instead of a `1px solid var(--border)` outline; a plain gray border is now reserved specifically for indicating an *actively selected or being-edited* item (e.g. `.event-card-editing`, `.calendar-cell-selected`, the active `.type-toggle` tab) — several of these use a `border: 1px solid transparent` base specifically so the selected/active state's own `border-color` override doesn't shift layout when it lights up. The one deliberate exception is the two structural data-grid tables, `AssignmentGrid`'s `.assignment-grid`/`.assignment-grid-wrap` and `SplitRecorder`'s CSS-Grid equivalent — their borders are real grid-line structure (sticky-column table layout), not decoration, and should never be stripped, only softened via the shared `--border` token's own value. The page background (`--bg`) is deliberately a light gray-tinted off-white rather than pure white, so white/`--surface` cards read as visually lifted off it.

**Color roles**: `--accent`/`--accent-dark`/etc (team-customizable, see "Team color theming" above) still drive *both* nav-active-state highlights *and* every primary action button (Save/Create/Assign/etc) — a team's own chosen color, blue by default. `--nav-text` is a separate, fixed, non-customizable neutral gray for inactive nav links and section-header icons (`.page-title-icon`, prepended to every main page's `<h1>`) — decoration/navigation chrome that shouldn't carry either the team's brand color or read as an action. Sport-type/event-category colors (see above) remain their own fixed, theme-independent set, as before.

**Icons**: `@tabler/icons-react` is the one icon set used throughout — both `NavBar`/`BottomNav`'s nav links and every main page's `<h1>` pair the same icon per section (e.g. `IconCalendarEvent` for Calendar, `IconClipboardList` for Workouts) so the same destination always reads with the same icon whether you reach it from the nav or the page title itself.

### Deployment: Cloudflare Workers

Live at a `*.workers.dev` URL, GitHub-connected via Cloudflare's Workers Builds — every push to `main` triggers an automatic build (`npm run build`) and deploy (`npx wrangler deploy`), no manual deploy step. `wrangler.jsonc` configures this as a static-assets Worker (`assets.directory: "./dist"`, `not_found_handling: "single-page-application"` so client-side routes don't 404 on direct navigation), not a Worker with its own server-side code.

Build-time environment variables (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_VAPID_PUBLIC_KEY`, `NODE_VERSION=20`) live in the Cloudflare dashboard under the Worker's **Settings → Builds → Variables and Secrets** — note this is a *different* "Variables and Secrets" screen than the one under the Worker's general Settings, which is for runtime bindings and doesn't apply to an assets-only Worker at all (the dashboard refuses to let you add anything there). A missing or wrong-scoped variable here doesn't fail the build — it just silently produces a working-looking site with that one feature broken (e.g. the push-notifications toggle throwing "not configured" with no other symptom). `wrangler deploy` logging **"No updated asset files to upload"** instead of listing new files is a strong tell that the build output didn't actually change — i.e. whatever variable you just added still isn't reaching the build, and it's worth re-checking it landed in the right "Variables and Secrets" screen before assuming the rebuild itself is broken.

Node version pinning matters here for the same reason `nvm use 20` is needed locally: the repo's default `node` is too old for this Vite version, and Cloudflare's build environment needs its own `NODE_VERSION` variable to pick a newer one.
